# Browser Extensions: independent versions and build/release ownership

**Code and packaging acceptance scope, 2026-10-10.** Actual installed
Tampermonkey/Chromium operation, real-account source backups, extension-ID
cutover and publication remain separately gated acceptance levels.

## Current version matrix

| Product | Version authority | Entry point | Tampermonkey | MV3 | Publication |
| --- | --- | --- | --- | --- | --- |
| VK Booster | CI Git ledger | `modules/vk-booster` | Separate VK only | Separate VK only | Independently tagged |
| ChatGPT Booster | CI Git ledger | `modules/chatgpt-booster` | Separate ChatGPT only | Separate ChatGPT observer, worker, popup | Independently tagged, manual approval |
| All-in-one | CI Git ledger | `apps/userscript/src/all-in-one.ts`, `apps/extension/src/all-in-one-content.ts` | VK and ChatGPT by site | VK plus ChatGPT observer and worker | Own tag/channel, manual approval |

`apps/all-in-one.json` declares dependencies on VK and ChatGPT. Its one
Control Center and feature registry select the corresponding provider on the
current host; no provider source data is silently uploaded or copied between
sites. The plain VK target retains the exact preexisting `content.ts` and
`popup.ts` entry behavior. ChatGPT standalone and all-in-one reuse the same
factory composition per target. No duplicated provider archive engine is
compiled for different distribution targets.

## Version-change graph

| Changed implementation | Required version change | Must remain unchanged |
| --- | --- | --- |
| `modules/chatgpt-booster/**` | ChatGPT and all-in-one | VK |
| `modules/vk-booster/**` | VK and all-in-one | ChatGPT |

| Documentation-only or CI-only | None | All product versions |

Published versions have one authority: `release-versions.json` on the `dev`
distribution branch, written by serialized trusted CI. Source manifests have
no product version field. Private workspace packages use fixed `0.0.0`
metadata; it is not a product version and is never shipped as an update.

### One version step per commit

Agents do not run a version writer or maintain a numeric matrix. After source
CI succeeds, `prepare-release-versions.ts` selects affected products, reads the
Git ledger and assigns each product one version for the source SHA. Ordinary
commits default to patch; scoped relevant `feat:` commits select minor;
`type!:` or `BREAKING CHANGE:` select major. Combined changes take the largest
one step, rather than adding increments for each edit. Documentation-only
changes select no products. The consumer graph includes dependent aggregates.

The assignment is committed to `dev` before building. A failed build or
publication retry for the same source reuses it, including a partially
published multi-product release. Stale source runs cannot advance the channel.
DEV userscripts, Chromium metadata, runtime UI and an approved PROD build all
consume that assigned version without a second DEV counter. Channel identities,
storage and approval gates remain separate. CI never writes a version commit
back to `main` and never creates a build loop.

The first transition seeds from the installed DEV userscript versions and
rolling tags, preserving update order. Subsequent runs use only the Git ledger.
Local builds read the fetched ledger without allocating anything; a checkout
without published refs exposes unassigned metadata and refuses packaging. CI fails closed if
its version baseline is unavailable. Fetch `origin/dev` and tags to refresh a
local checkout. A product version assignment is not proof of browser acceptance.

A successful build produces three separate userscripts and Chromium ZIPs.
`bun scripts/validate.ts --built` verifies their versions, independently
scoped updates, embedded module identifiers, MV3 script/world/host constraints
and permission isolation.

## Release operation and safety

Releases are generated by one manual-only workflow on `main` with mandatory
`approve_release=true` and dependency-aware `release_scope`. The scope
**defaults to `none`**, so it must be explicitly changed before publication:

- `chatgpt-booster`: only ChatGPT and all-in-one eligible;
- `vk-booster`: only VK and all-in-one eligible;
- `all-in-one`: only aggregator eligible;
- `all`/`shared`: all releasable modules eligible.

Module-scoped tags (`chatgpt-booster/v2.0.13`, `vk-booster/v1.0.0` for
first PROD only, etc.)
and stable Tampermonkey distribution branch paths prevent a release of one
module from changing another module's update channel. The workflow never
runs automatically from a source integration merge. A clean CI build is
**not** production acceptance of an installed extension or a statement that
old user data has been migrated.

## Decomposition review against VK

The VK runtime separates its source API, media mapping, state/selection,
offline viewer and Archive Manager presentation, and consumes shared
`packages/archive`, `packages/storage`, `packages/widgets`, `packages/ui` and
`packages/shell` surfaces. ChatGPT has separate provider packages for
`core`, `chatgpt`, `observer`, `telemetry`, `features`, `ui`, `userscript`
and `extension` and uses the same shared runtime, shell and archive helpers.
Standalone and all-in-one are now thin composition/delivery entries.

ChatGPT's `archive-v4-store.ts` and `archive-canonical-migrator.ts` remain
large provider-owned implementations, respectively roughly 2200 and 1900
source lines. They are **not** mechanically replaced by VK's linear
checkpoint engine: ChatGPT's native branch graphs, verified account identity,
source fingerprints, v3/v4 IndexedDB and canonical recovery invariants are
different. The `integrations/chatgpt-booster/` historical decomposition is a
non-distributed reference, not a second shipped module. The remaining
provider-specific decomposition and installed-browser acceptance should be
tracked separately rather than weakening these storage contracts for a
release shortcut.

## Shared storage refactor versions

The subsequent cross-provider `packages/storage` change intentionally bumps
VK Booster 2.3.10, ChatGPT Booster 2.0.3 and all-in-one 0.5.2. This is a
shared implementation change, not a VK-only or ChatGPT-only version bump.
The independent rules for future provider-only changes remain unchanged.
See [ARCHIVE_DECOMPOSITION.md](chatgpt-booster/ARCHIVE_DECOMPOSITION.md).

## Provider-only canonical decomposition milestone

ChatGPT's reader, partial-export and read-only audit services were extracted
from the migration coordinator with unchanged storage and source contracts.
The versions change only for ChatGPT **2.0.4** and its dependent all-in-one
**0.5.3**; VK stays **2.3.10**. Automatic, isolated DEV prereleases may follow
validated main CI; PROD remains explicitly approved.

### Channel-only lockfile metadata reconciliation

The DEV candidate planner distinguishes private product workspace-version
metadata in `bun.lock` from actual shared dependency updates. A ChatGPT-only
implementation and internal version bump now advances ChatGPT and all-in-one
DEV only; unrelated VK remains on its previous DEV build. Genuine shared
lockfile changes continue to rebuild/release all affected consumers.
